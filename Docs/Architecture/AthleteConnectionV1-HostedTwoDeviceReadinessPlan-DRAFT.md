## 3. Native test registration — a genuine, newly-found gap

### 3.1 Finding

**Method (reproducible, restated per ChatGPT review R3):** every `*.swift` file under `Tests/VoxtrSprint0Tests/` was listed directly via `git ls-tree` against the SHA named in §1.1; each file's exact basename was then checked for a literal matching `path = ...;`/`name = ...;` entry in `App/Voxtr.xcodeproj/project.pbxproj` via direct string search — not inferred from any prior PR's own count. By this method, of 98 such files, **35 have no matching basename anywhere in the project file**, as observed today against this document's own stated baseline.

**On the 35 vs. 36 vs. ~48 discrepancy: this document does not reconcile these figures and withdraws its earlier speculation about why they differ.** [Issue #113's authorization comment](https://github.com/cristern/Voxtr/issues/113#issuecomment-6106355509) itself references "36 pre-existing omissions"; a separate, earlier project-status checkpoint entry states "~48." This inspection has no access to either prior figure's exact method (same directory scope, same point in git history, same basename-match technique, or something else) and attributing the gap to "one file's status changed since that comment was written" — as an earlier draft of this document asserted — was this document's own unsubstantiated guess, not a verified fact, and is withdrawn per the reviewer's correction. The only figure this document stands behind is **35**, produced by the stated method against the stated SHA, as of this writing. A rough `grep -c "@Test("` over those 35 files totals approximately 694 test-attribute occurrences — reported as an approximate, grep-based count, not an authoritative one, since this sandbox has no Swift toolchain to compile or enumerate them definitively.

**The one specific instance worth naming individually:** `AthleteShellRoutingTests.swift` is among the 35. This file already existed before PR #120 (created in the original Athlete App shell foundation commit) and was specifically extended during PR #120's own R1 review-fix round to add tests for `AthleteShellRoute.route(legacyState:backendState:)` and `AthleteShellRoute.backendStatusNotice(for:)` — the exact routing logic R1 found was letting a legacy-connected device mask an observed backend denial. The file currently contains 29 `@Test` methods.

**Scope correction (ChatGPT review R3):** the prior wording claimed none of these tests "has ever compiled or run under any CI build to date," stated without qualification. That overclaims. `Package.swift:191` separately declares `VoxtrSprint0Tests` as an SPM `testTarget`, independent of the native Xcode target that `project.pbxproj` governs — a file absent from `project.pbxproj` can still be picked up and compiled/run via `swift test` against that SPM target. What this document can actually verify, directly in `codemagic.yaml`: Codemagic's own CI workflows invoke `xcodebuild test` against the native Xcode target exclusively, and never invoke `swift test`. So the accurate claim is narrower: **this file has never compiled or run under Codemagic's own CI to date**, including PR #120's own green build 283 — not that it has never compiled or run by any means, anywhere. Per CLAUDE.md §7 ("Do not rely only on local static reasoning when Codemagic is the authoritative compiler/test gate"), Codemagic is the relevant authoritative gate for this document's purposes, but the broader claim is not one this document can make. The 1,064-identity count [independently confirmed on PR #120](https://github.com/cristern/Voxtr/pull/120#issuecomment-6105684850) does not include this file under the native target — it was already absent before PR #120 touched it, and PR #120 did not add it to `project.pbxproj` either.

### 3.2 Why this matters for hosted/two-device readiness specifically

This is not merely a test-count bookkeeping issue, and (ChatGPT review R3's correction) it is not accurate to describe the underlying denial behavior as having zero automated regression coverage today. `AthleteBackendConnectionCoordinatorTests.swift` — registered in `project.pbxproj`, confirmed compiling and running under Codemagic CI — already covers the coordinator-state-level outcomes directly: `grantRevokedReportsGrantRevoked()` (lines 398-406) asserts a specific `.grantRevoked` coordinator state when the backend reports an actual grant revocation; `grantUnavailableFailureReportsConnectionUnavailable()` (lines 422-433) asserts the neutral `.connectionUnavailable` state for `SessionFailure.grantUnavailable`; and a `restoreOnLaunchOrForeground` test exercises a forced online check denied with `.grantUnavailable`, confirming it overwrites a cached presentation. That coverage runs green under Codemagic today and is not in question.

**What specifically lacks Codemagic CI coverage is one layer up:** the `AthleteShellRoute.route(legacyState:backendState:)` and `AthleteShellRoute.backendStatusNotice(for:)` routing/banner logic exercised in `AthleteShellRoutingTests.swift` — the exact surface R1's own fix touched, translating a coordinator state the tests above already prove is correctly distinguished into what the Athlete-side UI shell actually displays. The coordinator-level distinction between `grantRevoked` and `connectionUnavailable` is proven by registered, CI-running tests; whether the shell-level routing correctly refuses to let a legacy-connected display mask that distinction — the specific regression R1 found and fixed — is the part this document finds currently unverified by Codemagic CI, not "zero coverage of the behavior" in the broader sense the earlier wording implied. This does not mean the behavior is wrong — direct source inspection in the PR #120 delivery history shows the fix was made and independently delta-reviewed against the diff — but it means the only thing currently guarding against a regression at the routing/banner layer specifically is manual review, not CI.

### 3.3 Recommendation

Registering all 35 files at once in the same change that touches production code risks surfacing long-dormant failures from code paths that have genuinely never been compiled or run before, mixed in with unrelated work — exactly the risk the PR #119 review (which found and deliberately did not fix this same class of gap beyond its own three new files) already flagged. This document recommends a dedicated, bounded, test-registration-only follow-up task — scoped to adding file references and nothing else, reviewed for compile/pass status in isolation — before, or in parallel with, hosted execution; it does not itself perform that registration.

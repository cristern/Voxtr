# Athlete Connection V1 — Normative security contract

**Status:** Product behavior approved 2026-09-21; technical implementation contract for review in PR #97. **No authorization code or migration is authorized merely by creating this document.** The Product Constitution and living Architecture have precedence; [ADR](ADR-AthleteConnection-BackendAuthorization.md) records the backend decision. [Recovered original API report and correction ledger](AthleteConnectionV1-RecoveredAPIContract.md) is provenance only: its invalid CloudKit `recordChangeTag` proof and signing-key encryption must never be implemented. The final normative API/SQL details below are **proposed implementation specifications**, distinct from Product Owner-approved behavioral outcomes. Changes affecting trust, identity, data exposure or offline access require review and explicit approval before implementation.

## 1. Purpose and actors — approved

A Parent physically present with an athlete chooses one **existing** `AthleteProfile`, presents a QR, compares a code shown on the athlete's actual installation, and explicitly approves that installation. The QR invites a request only; it does not authenticate a Parent, authorize data disclosure, establish a grant, or establish an athlete's real-world identity. The same immutable canonical `workspaceId`, `participantId` and `athleteId` are preserved. The authorized Athlete installation may hydrate only the selected athlete after approval; no sibling/name/order/age heuristics.

Authoritative owners: iOS domain owns `FamilyWorkspace`, `AthleteProfile`, `WorkspaceParticipant` membership, Planning/Training/Reflection; Vǫxtr authorization backend owns invitation, request, device grant, and session authorization. CloudKit remains the separate business-data sync transport. No profile replica, general athlete-account system or CloudKit public-share pairing.

## 2. Approved product decisions, exact scope

- Invitation TTL **15 minutes** from server/database creation time; server checks expiry, including approval and claim. Expired invitations cannot generate a first grant.
- One **successful connection/grant per invitation** despite competing requests, parallel claims, dropped responses and retries. The database is authoritative.
- Parent reviews one pending request, verifies its device-specific comparison code against the physical AthleteApp, and explicitly approves it before a device grant can be claimed.
- **Protected HTTPS transfer**: backend may temporarily process only necessary hydration data; backend does not need end-to-end opaque ciphertext. An anonymous QR holder, other request, other device, unapproved request, or revoked grant may not retrieve hydration data. No assertion of server-operator inability to read plaintext.
- Interrupted activation: **same approved installation can resume for up to 24 hours** without another Parent approval. Temporarily retained hydration data are deleted after verified hydration completion or no later than the 24-hour deadline. Retention is not a grant lifetime extension or a way to bypass revocation. If activation has not succeeded by the deadline, no further payload is served and a new pairing is necessary.
- Offline: already-downloaded data remain locally viewable with a calm, unambiguous **"connection cannot be verified"** state. No new protected synchronization operations without renewed authorization. A server revocation cannot physically erase or retroactively control downloaded offline bytes. The UI must not claim the connection remains verified while offline.
- Existing-workspace enrollment for **Internal Alpha only**: server-verified Sign in with Apple (SIWA) identity plus deliberate manual display-name/workspace confirmation, explicitly a **limited human trust enrollment**, not independently verified CloudKit ownership. An owner-account change is a **separate controlled process**, not automatically permitted by knowledge of `workspaceId`, display name or a new SIWA login. For new workspaces, bind verified SIWA identity at creation. Do not infer identity from `AccountId.pending` or silently overwrite it.

## 3. Trust boundaries and secrets — normative constraints

HTTPS protects requests in transit, not access control at rest or caller authorization. Backend must independently validate SIWA identity tokens (signature, issuer, audience, expiration and nonce if used) against Apple's current key material; client assertions, email/display names and CloudKit record tags are not server proof. Backend issues its own server-scoped Parent session bound to the enrolled workspace. A Parent session cannot access another workspace. An invitation identifier, QR, request ID, `grantId`, display code, or `athleteId` is **never a credential**.

Athlete request carries an installation-specific, hardware-backed P-256 **signing** public key where supported. The corresponding nonexportable key proves possession by signing fresh challenges. The comparison code supports human matching only; it is not authentication. Server must verify signatures against the stored approved request key, with bound request/grant identity, action, random nonce, issuance and expiry, one-use tracking, unambiguous canonical signed bytes and replay rejection. Signature keys are not encryption keys. When the app is reinstalled or loses the key, require a new pairing rather than silently reassigning grants. No key material, Apple tokens, session tokens, secrets or minor PII in URLs, QR, error text or logs.

No `anon`/`authenticated` direct privileges to backend authorization tables; use a private, non-Data-API-exposed schema with reviewed least-privilege service access and tightly scoped entry points. Do not put service-role keys or signing secrets in iOS. The Supabase `health` function is unrelated, intentionally public and **not deployed** by Foundation V1; do not reuse its `verify_jwt=false` configuration on sensitive endpoints. Never handle real minor/family data in the development project.

## 4. Invitation, request, approval, grant and session lifecycle — required invariants

**Invitation:** server creates random opaque ID and 15-minute DB-time deadline, fixed canonical workspace/participant/athlete scope. QR contains only minimal routing and opaque invitation reference; no names, birthdates, profile data, tokens or grants. Multiple request submissions can be handled without revealing another request's code or details. Unknown and expired public invitation handling must not leak workspace or athlete existence.

**Request:** submitting an installation public key creates a distinct server request ID and a random, request-bound comparison code returned only to that request's direct HTTPS response. The workspace-authorized Parent can list pending requests/codes for that workspace; only the exact chosen request is approved. Parent-facing code is for in-person confirmation; never treat a matching code alone as authorization. Rejection, expiration, grant consumption and revocation are distinguishable states. Only one request may be selected for approval per invitation; if prior approved request is replaced, the old request must be explicitly invalidated, and no second grant is possible.

**Claim:** after approval, approved installation obtains a fresh bounded challenge; server verifies its signed proof before any grant/payload response. Claim occurs atomically with invitation consumption and grant creation in the database. Enforce `UNIQUE(grants.invitation_id)` plus row lock on **invitation**, not only request (`SELECT ... FOR UPDATE OF i` or an equivalent proven atomic pattern), check `expires_at > database_time`, consumption and approval **inside** that transaction. Successful same-key retry retrieves the same grant and permitted recovery data, subject to active grant and recovery deadline; it never creates another grant. Another key/request cannot use the first request's success. Return generic errors to unauthorized callers.

**Grant:** unique immutable grant ID binds the invitation, chosen canonical IDs, exact request and public key. Server-side status is sole authority for device authorization. A workspace membership row is not a grant. Parent revocation marks the server grant revoked, prevents further claim retries from delivering payload, blocks session renewal and every subsequent **online sensitive operation** even if an otherwise unexpired bearer token exists. Grant IDs alone never grant access.

**Session:** server-issued opaque or signed session scoped to grant, device, workspace and intended actions; short-lived credentials stored only in device-protected Keychain. Refresh requires proof of possession of that grant's key and checks the active grant. Sensitive handlers validate session AND currently active grant on each call; token expiry alone does not implement immediate online revocation. After reinstall/key loss, old sessions cannot transfer authorization to a new key. Exact session TTL, token format and refresh nonce parameters are engineering selections to verify before implementation, **not approved values from the recovered report's circa-one-hour example**.

## 5. Hydration and 24-hour recovery — approved behavior and implementation requirements

Parent provides the minimal snapshot required by the actual canonical initializers only after authorizing the exact request. Protect submission with workspace-authenticated Parent session and TLS. Never expose payload via invitation/unauthenticated request or public Supabase tables; scope retrieval to the approved, proof-of-possession-authenticated installation with a currently active grant. Choose bounded server-side storage (protected private table or equivalent) only if needed for idempotent lost-response recovery; account for data including a minor's name and birth date as sensitive plaintext at rest, minimize fields, permissions, logging and database backups. Explicitly document storage/access controls, provider retention/backups and deletion limits before live data use; deleting a row does not guarantee immediate destruction of immutable backups.

The **24-hour deadline** starts at first successful grant/activation transaction (server time), cannot be reset by retry, must not exceed any separate invitation expiry to authorize a *new* initial claim, and is checked by server on every payload fetch. A grant created before invitation expiry may re-deliver to its **same proven key** within 24 hours even after invitation expiry. Successful authenticated `hydration-complete` acknowledgement deletes retained payload early; automatic cleanup deletes remaining eligible payload no later than retention deadline, with failed cleanup visible to operations. Revocation immediately denies online access and triggers payload removal; offline cached data cannot be recalled. If interrupted before a grant was created, the expired 15-minute invitation cannot be revived; create a new invitation. Failed hydration must not create a second athlete identity or synthetic local grant.

**Integration boundary:** CloudKit business sync authorization remains a separate verified integration requirement; possession of a backend grant must not be described as independently revoking already accepted CloudKit shares or recalling locally synced records. End-to-end access control of any future shared CloudKit records needs its own testable mechanism before deployment.

## 6. Parent enrollment and account recovery

**New workspace:** require verified SIWA Parent subject bound server-side as workspace is first created, before allowing invitations. Bind identity through an authenticated creation transaction, not first-registration-wins by UUID alone. Preserve canonical ownership in the iOS workspace domain; the backend mapping only authenticates the workspace-scoped operator. Any migration from `AccountId.pending` needs an explicit versioned, conflict-safe plan.

**Existing workspace (Internal Alpha only):** show the actual workspace name and an explicit human confirmation; verify SIWA identity server-side, record enrollment scope, time and audit provenance, ensure enrollment cannot silently transfer an existing workspace binding. This is a consciously accepted trust limitation, not a CloudKit/SIWA cryptographic ownership proof. The PR #96 CloudKit Web Auth Token exploration was not live-verified and cannot prove SIWA-to-CloudKit identity equality. Never implement the recovered report's client-returned `recordChangeTag + nonce` as independent proof. Owner-account changes or competing enrollment require denial and a separate controlled recovery process, with operator involvement and auditable verified evidence; **the detailed recovery protocol is a separately scoped decision, not self-service rebind**. Limit enrollment to Internal Alpha until stronger verification is reviewed.

## 7. API contract: stable roles and non-negotiable checks, not fabricated wire format

The recovered report proposes `/v1/parent/register`, `/v1/invitations`, `/v1/invitations/{id}/requests`, `/v1/workspaces/{id}/requests`, `/v1/requests/{id}/approve|reject|challenge|claim|hydration-complete`, `/v1/grants/{id}|refresh|revoke`. These names are **historical candidate paths**, not approved final URLs. The implementation specification must define exact route, method, token placement, challenge bytes, input limits, state transition conditions, idempotency response, error codes, cache headers, rate limits and sensitive-field inventory before a route is built. This document fixes each route's role requirements and lifecycle invariants above; it does **not** falsely declare missing exact wire fields normative. In particular remove invalid `recordChangeTag` proof and `encryptedPayload` signing-key claim from any future endpoint.

## 8. Required tests and release gates

Backend isolated CI must exercise real PostgreSQL transactions: competing claims for one invitation, same-key lost-response retry, different-key rejection, exact DB-time expiry, approval/rejection, wrong Parent/workspace, stolen QR/request/grant ID, expired challenges, nonce replay, active-session-after-revocation, recovery at/beyond 24 hours, cleanup and zero anonymous minor PII. Assert actual schema privileges and API exposure. Distinguish simulated Apple token tests from a real service verification and mocked signing tests from device Secure Enclave proof. Codemagic remains Swift compile gate; TestFlight on **two physical iPhones** is runtime gate for approval/code matching, exact athlete/sibling isolation, interruption and retry, offline warning, revocation and reinstall. Real-data testing is prohibited in `voxtr-auth-dev`.

## 9. Remaining engineering design gates (not new product choices)

Before migration or API implementation, review and freeze: corrected Parent enrollment wire protocol for new vs existing workspaces; SIWA token/session verification and safe onboarding race policy; full state enums, status-transition diagram, schema constraints and cleanup; challenge protocol byte canonicalization/replay storage; precise session TTL and token lifetime; protected hydration field inventory, storage encryption/access limits and backup/retention semantics; abuse/rate-limit controls; explicit CloudKit sync/revocation boundary; controlled owner-account recovery procedure. These are bounded security engineering design questions, **not permission to change the six approved user-facing outcomes**. A proposed default must be explicitly called a proposal, never claimed previously approved.

## 1. Purpose and ownership — APPROVED

Parent chooses an **existing** `AthleteProfile`, presents nearby QR, visually compares a code on the actual Athlete installation and explicitly approves that exact request. QR possession never provides authorization, hydration, Parent identity or proof of the athlete's real-world identity. Preserve immutable canonical `workspaceId`, `participantId`, `athleteId` and sibling isolation; no name/order/age matching. iOS domain remains authority for `FamilyWorkspace`, `AthleteProfile`, `WorkspaceParticipant` membership and Planning/Training/Reflection. Narrow Supabase authorization backend owns invitations, connection requests, installation grants and their sessions/revocation; CloudKit continues as **separate business-sync transport** rather than CKShare invitation authority. `AthleteAccessGrant` in the iOS domain is **not automatically the backend installation grant**; migration/integration must not conflate them.

## 2. Product Owner-approved exact behavior

1. An invitation expires **15 minutes from authoritative backend/database creation time**; an expired invitation can never create a *first* grant. Server enforces this regardless of device clock.
2. Exactly **one successful installation grant per invitation** even across two requests, retries, concurrent claims and dropped HTTP responses; enforce with real database transaction and uniqueness.
3. Parent must authorize the selected request after comparing its independently delivered code. The code is for human request identification, not an auth token; a forwarded QR holder can submit a different request but must never access the chosen athlete's identity or hydration data.
4. **D1 — HTTPS:** after specific Parent approval, backend may temporarily process the minimum required plaintext hydration data over protected HTTPS. Only the approved installation with verified device credential and active authorization can retrieve it. No end-to-end encryption guarantee and no anonymous QR-level PII.
5. **D2 — 24-hour same-installation recovery:** same proven device can resume within a fixed 24-hour window beginning at the first successfully committed grant; no new grant/approval and no invitation revival. Retained sensitive payload is deleted on verified completion or expiration. Server must deny all payload reads synchronously after deadline even if deletion job fails; at-rest/backup erasure and operations need precise, truthful documented guarantees before real data, not an assertion that provider backups vanish at row deletion.
6. **D3 — offline:** previously cached data remain viewable while offline, with clear calm "connection cannot be verified" state; no new protected sync while authorization cannot be checked. Server revocation immediately blocks **subsequent online sensitive backend requests**. Offline bytes cannot be remotely erased. Backend revocation does **not** by itself revoke independent CloudKit business-sync access; this cross-domain integration is a separate runtime/release gate.
7. **D4 — existing workspace Internal Alpha:** server verifies Sign in with Apple identity and Parent deliberately confirms workspace/display name; this is a **limited human trust step**, never claimed to cryptographically prove CloudKit owner identity. A change of owner account requires separate controlled procedure, not automatic re-binding. New workspaces must bind a verified SIWA subject on creation; `AccountId.pending` never counts as verified identity.

## 3. Mandatory technical guarantees, not endorsements of a specific wire syntax

- Independently verify SIWA token with Apple public key and correct issuer, audience, expiry, nonce as applicable; Apple SIWA `sub` and CloudKit identity are distinct. Client-supplied `recordChangeTag` + nonce cannot prove record access to an independent server. The prior ownership spike is isolated/compile-only, no live Apple round trip or cryptographic SIWA↔CloudKit binding.
- Fresh installation-specific P-256 **signing** key (Secure Enclave where supported) proves possession through request/purpose-bound fresh signed challenges; comparison code is only a human visual check. Signing keys are not encryption keys. Exact canonical signing bytes, nonce use/expiry, public-key/signature encoding and Swift↔backend compatibility require explicit reviewed test vectors before implementation.
- `invitationId`, `requestId`, `grantId`, QR IDs and display codes are identifiers, **not bearer authority**. Scope authenticated Parent to enrolled workspace; scope athlete session to approved request, exact key/grant and intended IDs. Active grant must be checked for every sensitive online operation, not just session issuance/refresh; compromised bearer-token exposure must be considered for hydration and mitigated with device-key proof.
- Use backend-issued session, stored device-only in Keychain; never UserDefaults authorization truth. A reinstall/lost signing key is a new installation requiring pairing. Exact token format, TTL and refresh mechanism are engineering proposals only until review.
- First successful claim must lock the **invitation row** and re-evaluate expiry using current database time after lock acquisition, then consume invitation + insert single grant atomically, with database UNIQUE(invitation_id). Same-key retry must authenticate anew and return the **same existing grant** only if active and within the 24-hour recovery deadline. Another request/key must not access it.
- Backend authorization tables are private, not exposed through Data API nor directly accessible to `anon`/`authenticated`, with permission/RLS auditing. Service-role secrets and Apple/private credentials remain server-only. No PII or secrets in QR, URL, logs, public errors, or public health endpoint. Rate limits, size limits, cleanup and safe fault responses require review.
- `verify_jwt=false` on a custom-auth Supabase function is **not itself insecure or secure**: it disables the platform's Supabase-JWT admission check; the function MUST then independently authenticate the exact intended Apple/Vǫxtr credential and authorize every sensitive operation. Do not copy unauthenticated `health` behavior to business endpoints or assume Supabase platform JWT validation understands Apple tokens.
- Backend escrow uses minimum snapshot of existing canonical fields only after Parent authorization, with at-rest protection, restricted data lifecycle and truthful backups. No profile/Planning/Training/Reflection duplication as permanent backend truth.

## 4. State and acceptance requirements

Invitation issued → consumed or expired; pending request → approved/rejected and approved → claimed only as part of atomic grant transaction; active grant → revoked irreversibly; session can expire/be invalidated and does not create a grant; escrow is available to the same approved key only before recovery deadline and cleared on acknowledgement/revoke/deadline. Actual SQL enums/transitions and exact error codes must be reconciled with [technical review](AthleteConnectionV1-TechnicalProtocolReview.md), not inferred from historical sample DDL.

Tests must exercise real isolated PostgreSQL transactions: simultaneous claims, uniqueness, same-key lost-response retry, wrong key/workspace/Parent, expired invite under lock wait, request approval races, nonce replay, revoked session, 24-hour boundary, no unauthenticated minor PII, schema privileges, deletion/read-denial and failure injection. Fake Apple/Secure Enclave tests are not genuine Apple-device proofs. Codemagic compile and **two physical iPhones in TestFlight** validate actual approval, selected sibling identity, recovery, offline, reinstall and revocation. Independently verify CloudKit sync scope/revocation before calling overall pairing secure. Never use real child/family data in `voxtr-auth-dev`.

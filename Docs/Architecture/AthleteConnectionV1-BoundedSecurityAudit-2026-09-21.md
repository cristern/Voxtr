## A. Existing-workspace owner enrollment — status: NOT CLOSED

**Verified source:** `Docs/AthleteConnectionOwnershipVerificationSpike.md` says the CloudKit Web Auth Token proof was compile-only, not live-tested, and does not cryptographically bind CloudKit identity to a Sign in with Apple `sub`. `Sources/VoxtrAppShell/AthleteIdentityHydrationService.swift` creates ParentProfile and FamilyWorkspace on the fresh athlete device using `AccountId.pending` and `technicalOwnerAccountId: .pending`; these are bootstrap placeholders, not identity evidence. Backend Foundation has no ownership mapping or auth implementation yet.

**Approved product contract:** new workspaces bind the authenticated Parent's SIWA identity during workspace creation; existing workspaces use the expressly limited, manual Internal Alpha enrollment; an owner account change is never automatic. Confirming a workspace display name or knowing UUID does not independently establish ownership.

**Residual threat:** first caller who guesses/obtains `workspaceId` and display name could self-enroll if API simply implements first-writer-wins. SIWA proves the caller's Apple account, not ownership of the claimed local workspace. A one-time challenge from the app cannot fix that without independent ownership evidence.

**Bounded technical proposal for review:** owner enrollment for pre-existing workspaces is restricted to an operator-maintained Internal Alpha allowlist/approved test cohort with explicit out-of-band confirmation and audit event; reject unauthorized, conflicting or repeated SIWA subjects. Only Parent-initiated, never background auto-enroll. Specify precise trusted bootstrap/provisioning authority, conflict rules, audit fields, non-PII support flow and safe treatment of an already-bound workspace before coding. Do not call this cryptographic CloudKit ownership verification. Full owner-change recovery remains a separate task. This proposal is NOT yet live-validated or approved as a particular operator procedure.

**Gate:** a reviewed, concrete enrollment protocol plus negative tests for arbitrary UUID, duplicate binding, different SIWA subject and race; no live existing-family enrollment before this is complete.

## B. 24-hour hydration retention — status: LOGICAL EXPIRY CONTRACT CLOSED; PHYSICAL DELETION NOT VERIFIED

**Approved product behavior:** only the same approved key-authenticated device can resume up to 24 hours after first successful grant; payload deleted after authenticated completion or deadline. Revoked grants cannot retrieve payload; server must deny at the deadline even if a cleanup job fails. A first grant still requires an unexpired 15-minute invitation.

**Provider evidence (accessed 2026-09-21):** Supabase pricing states the Free plan has **no automatic database backups or PITR**; Pro has seven days of automatic backups and longer features exist in other plans. Supabase backup documentation confirms backup and point-in-time restoration depend on plan/settings and recommends off-site manual backups for Free projects. Sources: https://supabase.com/pricing and https://supabase.com/docs/guides/platform/backups . This is plan documentation, NOT verification of the account's currently enabled settings or all provider infrastructure/log/subprocessor retention. Future upgrades, snapshots, logical dumps or exports may retain data beyond row deletion.

**Design requirement:** minimize hydrated fields; private database schema and strict access; encrypted-at-rest service-managed storage where available; never include sensitive payload in log, URL, error, analytics, traces, or backup/export workflows. Store `grant_created_at`, fixed `payload_expires_at = grant_created_at + 24h`, and `hydration_completed_at`; enforce eligibility on every payload read using a current server/database clock and active grant. Acknowledgment causes immediate application-row deletion; a scheduled cleanup removes expired rows and has monitoring/retry for failures. No retry may reset expiry. On revocation deny access immediately and enqueue/delete escrow row. Provider backup retention and any exported copies must be separately documented before processing real minors' data. Do not promise physical destruction of every backup at the 24-hour mark; that was not approved as an independently demonstrated provider capability.

**Gate:** verify actual project plan, database backup/PITR/export settings, function/request log retention, encryption/access configuration and service retention terms in provider dashboard; record operational owner and policy. Test deadline access denial with cleanup disabled, completion deletion, revocation and failed cleanup alarm. No real family data in `voxtr-auth-dev`.

## C. CloudKit scope and revocation — status: CURRENT PAIRING EXPOSURE IDENTIFIED; FUTURE BUSINESS-SYNC GATE OPEN

**Verified repository:** `CloudKit/VoxtrCloudKitSchemaManifest.md` lists exactly two mapped Vǫxtr application record types: `FamilyWorkspace` and `AthleteConnectionInvitation`; no Planning/Training/Reflection CKRecords in this manifest. It also states `CKSyncEngine.nextRecordZoneChangeBatch` always returns `nil`, i.e. no record type currently mapped to a sync-engine change batch. `FamilyWorkspaceOwnerShareCoordinator.ensureShare` creates a separate root `CKShare` with `publicPermission = .none`, no participant invitation; `FamilyWorkspaceParticipantShareCoordinator.resolveAcceptedShare` accepts/fetches the *invitation* share in Athlete's `.shared` database and decodes its hydration projection; `AthleteConnectionLifecycleService.connect` then hydrates local SwiftData and activates the actor. `AthleteConnectionInvitationCloudRecordMapping` includes minor's given name and birth date in this old transport record. PR #95 proposes making that invitation share public `.readOnly` and remains open/unmerged: do not use it.

**Precise conclusion:** source presently demonstrates a legacy invitation-specific CloudKit transport and a non-public root share, **not an implemented, live-proven full CloudKit business-data synchronization system**. The proposed backend grant cannot revoke old invitation CKShares already accepted and cannot erase data previously saved locally. There is no evidence in these inspected files of a completed protected CloudKit Planning/Training/Reflection access path to declare revocable. Avoid both false claims: that all business sync already works, and that backend revocation automatically revokes all CloudKit permissions.

**Required implementation boundary:** replace invitation CKShare pairing/PII hydration with approved backend flow; inventory any existing accepted shares/root zones, specify lifecycle for removing/disabling obsolete invitation shares, and decide how legacy devices are migrated or blocked. If a future separate CloudKit business-data sharing implementation is added, require an independently enforceable permission/revocation design with two-device tests before enabling it. Backend revoke must deny all subsequent backend sensitive operations and UI must report offline data limitations truthfully. Do not remove CloudKit wholesale or assume an unimplemented business-sync pipeline exists.

**Gate:** bounded repo-wide call-site and cloud schema audit (`CKShare`, `accept`, `removeParticipant`, `revoke`, `CKSyncEngine`, all shared-record mappings) covering actual source HEAD, not only comments; verify any real already-accepted shares on two physical devices and whether their old invitation records remain readable after revoke; determine necessary cleanup/migration as a separate PR with Codemagic/TestFlight validation. If this audit finds an actual independent business data access route, document its authorization controls separately.

## Cross-cutting provider authorization warning

Supabase's official auth documentation distinguishes platform `verify_jwt` (expects Supabase Auth JWT/platform-accepted keys) from application-level checks. A custom SIWA/Vǫxtr credential cannot be assumed validated just because `verify_jwt` is enabled or because a function was reachable. A function with `verify_jwt=false` requires a fail-closed handler that verifies the correct credential for every sensitive route. Sources: https://supabase.com/docs/guides/functions/auth and https://supabase.com/docs/guides/functions/auth-headers . Validate against actual deployed runtime before auth endpoint work.

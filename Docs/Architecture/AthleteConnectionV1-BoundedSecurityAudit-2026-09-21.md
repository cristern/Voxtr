## A. Existing-workspace owner enrollment — status: NOT CLOSED

**Repository evidence:** `Sources/VoxtrCoreContracts/Identifier.swift`, `Sources/VoxtrAppShell/AthleteIdentityHydrationService.swift`, `Sources/VoxtrParentDomain/ParentWorkspaceRepository.swift`: `AccountId.pending` and `technicalOwnerAccountId: .pending` are bootstrap values, not real owner identity. Issue #98 audit reports no `AuthenticationServices`/`ASAuthorization`/SIWA implementation in iOS `Sources/`/`App/` and no backend auth/enrollment code at backend `fcbab9b`. The isolated CK Web Auth Token spike never demonstrated a live Apple-service call or cryptographic link to SIWA `sub`.

**Approved product contract:** new workspaces must bind authenticated Parent SIWA identity at creation; existing workspaces may use a deliberately limited Internal Alpha manual enrollment, with controlled—not automatic—owner-account change. Neither display name, workspace UUID nor client-returned CloudKit tag proves ownership.

**Threat:** blind 'first SIWA subject claiming this UUID wins' grants a foreign Apple account control if a workspace identifier is obtained. A matching name or SIWA authentication proves neither existing workspace ownership nor consent.

**Bounded technical proposal awaiting review (not an additional approved product decision):** operator-controlled preauthorization for each existing Alpha workspace, with out-of-band confirmation against the genuine Parent before issuing a single-use, workspace-scoped enrollment permission. Server verifies the SIWA subject, binds one workspace to one subject with a uniqueness/conflict-safe transaction, rejects a different subject and records minimum auditable metadata (`workspaceId`, subject reference or pseudonym, authorization source/operator, outcome, event time; no names, tokens or minor PII in logs). A second owner or account replacement uses a separate reviewed recovery flow. Exact provisioning authority/storage and how that proof is issued and redeemed must be specified; do not allow public self-enrollment via guessed UUID or name. **The Product Owner-approved limited trust model is not itself approval of any particular operator tool or data-handling procedure.** New-workspace creation cannot be asserted atomic across local SwiftData and remote PostgreSQL; design coordinated identity binding, failure reconciliation and conflict rules without inventing a nonexistent cross-store transaction.

**Gate:** explicit, reviewed enrollment/provisioning contract, tests for unauthorized UUID, replay and conflicting SIWA subjects/concurrency, then limited TestFlight enrollment evidence. No real existing-family enrollment before that.

## B. 24-hour hydration retention — status: LOGICAL PRODUCT RULE APPROVED; HOSTED RETENTION UNVERIFIED

**Approved behavior:** a single grant created against an unexpired 15-minute invitation can be resumed by the *same proved installation* only within 24 hours of the first grant; delete transient payload upon authenticated completion or expiry, block read at the deadline regardless of cleanup; revocation blocks immediately online. No retry may restart the 24 hours.

**Repository evidence:** issue #98 audit independently reports only Foundation scaffold on backend develop: no escrow/storage, retention or backup settings implemented. The contract prescribes private storage, minimum fields and tests but these have not run.

**Provider evidence and limitation:** prior audit (2026-09-21) cited https://supabase.com/pricing and https://supabase.com/docs/guides/platform/backups for Free-plan absence of included automatic database backups/PITR and paid-tier offerings. Issue #98 auditor could not directly open these pages (`EGRESS_BLOCKED`) and instead obtained concordant **search summaries**. Thus its second pass is *not a fresh primary-source confirmation*; neither pass verified this specific `voxtr-auth-dev` project's dashboard, log retention, snapshots, exports, billing or backup configuration. Do not extrapolate Free-plan marketing features to all provider-held copies or promise backup erasure within 24h.

**Requirement and proposed controls:** server checks `payload_expires_at = first_grant_created_at + 24h` and active grant on each fetch using a current database/server clock, refuses reads at/after deadline even if cleanup job fails; authenticated completion deletes application payload row early; revocation denies access and removes queued/retained payload; scheduled cleanup with retry/visibility. Avoid PII in requests URLs, logs, analytics, traces and exports, document encryption/access and provider backup/retention. Row deletion is distinguishable from physical deletion of immutable backups.

**Gate:** a user/operator with dashboard access must record actual plan, backups/PITR, log/edge-function retention, exports, encryption/access controls and a realistic deletion policy before handling real families; isolated PostgreSQL tests for deadline with cleanup disabled, completion/revocation deletion and cleanup alarm. No real minor data in `voxtr-auth-dev` until approved data-handling gate.

## C. CloudKit scope/revocation — status: CURRENT CODE SCOPE AUDITED; DEVICE AND FUTURE SYNC GATES OPEN

**Second-pass source review reported by issue #98:** `CloudKit/VoxtrCloudKitSchemaManifest.md`, `AthleteConnectionInvitationCloudRecordMapping.swift` and coordinator mapping match two existing app CKRecord types, `FamilyWorkspace` and `AthleteConnectionInvitation`; 11 invitation payload fields include minor given name and birth date. `CloudKitTransport.ScopedDelegate.nextRecordZoneChangeBatch` returns `nil`, no Planning/Training/Reflection CKRecord mapping exists in the inspected manifest. `FamilyWorkspaceOwnerShareCoordinator.ensureShare` and `createInvitationShare` still specify `.publicPermission = .none` on `develop`; PR #95's proposed `.readOnly` remains open, unmerged. Participant-side flow accepts invitation CKShare and fetches invitation record; code search for CloudKit share deletion/participant removal reported no matches. `revokeInvitation` changes local SwiftData only. No implemented general CloudKit business-data sync was evidenced by the inspected mappings/call sites.

**Precise boundary:** the *legacy* invitation CKShare is a transport for a sensitive initial projection; it is not the approved backend design. Backend revocation cannot revoke an independently accepted CKShare, remote-erase previously hydrated SwiftData or revoke a future independently implemented CloudKit data share. Conversely, do not overstate a nonexistent current Planning/Training/Reflection CKRecord sync path as an exposed vulnerability. Actual past accepted shares on physical devices are unknown from code alone.

**Smallest proposed action:** replace legacy pairing/hydration invitation shares with backend-authorized flow, leave PR #95 unmerged. Inventory accepted invitation shares on real two-device TestFlight, then decide whether dormant legacy shares require explicit cleanup/retirement; do not add general CloudKit revocation machinery for a business-sync path not yet implemented. Any future business-sync path needs its own authorization/revocation design and tests, independent of the backend grant. Do not silently remove CloudKit overall.

**Gate:** TestFlight inventory and revocation/readability test for actual legacy accepted invitations, explicit migration/cleanup decision, separately evidenced CloudKit business-sync contract before advertising it as implemented or revocable. No runtime validation in issue #98.

## Cross-cutting implementation risks

Custom SIWA or Vǫxtr bearer tokens must be verified by the application's handler (correct issuer/audience/nonce/signature/expiry or session and active grant). Supabase `verify_jwt` is a platform precheck, not proof it validates an arbitrary Apple identity token or custom session. For a function whose platform JWT gate is disabled, fail-closed handler authorization on **every** sensitive route is mandatory; public Foundation `health` is not precedent for an unguarded endpoint. Proposed nonce TTL, session TTL and signature byte format are still engineering choices, not implemented or implicitly Product Owner-approved. Database invitation row lock, authoritative time evaluated *after acquiring lock*, grant uniqueness, replay/idempotency and sensitive-hydration field minimization require isolated actual tests. Never describe two data stores (local SwiftData and Postgres) as one atomic transaction.

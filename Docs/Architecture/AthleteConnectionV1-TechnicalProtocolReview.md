# Athlete Connection V1 — technical protocol review for approval

**Status: ENGINEERING PROPOSAL, not an approved or implemented API.** 2026-09-21. This document fills out the technical review requested after Product Owner approval of D1–D4. Review together with [approved behavior and security invariants](AthleteConnectionV1-NormativeSecurityContract.md), [decision ledger](AthleteConnectionV1-DecisionReview.md) and [historical corrected API inventory](AthleteConnectionV1-RecoveredAPIContract.md). Product Constitution → living Architecture → ADR remain authoritative. This document does **not** authorize coding, a migration, hosted operations, merging PR #97 or releasing Athlete Connection.

## A. Purpose and acceptance boundary

Pair one selected pre-existing `AthleteProfile` with one physical Athlete installation after Parent approval, with server-enforced 15-minute invitations, exactly one grant, safe 24-hour same-device recovery and online revocation. QR possession is not authorization. The service must not own `AthleteProfile`, `WorkspaceParticipant`, planning/training/reflection or general CloudKit synchronization. Design cannot claim successful remote revocation of CloudKit shares or deletion of offline data. **End-to-end production readiness is blocked until the independent CloudKit business-sync access control / revocation boundary is evidenced and tested**; backend grant alone cannot revoke a separately accepted CKShare.

## B. Architecture review findings — verified constraints versus choices

- The recovered final report's `recordChangeTag + nonce` supplied by client is **not** server-verifiable workspace ownership. The merged CK Web Auth Token spike neither establishes SIWA ↔ CloudKit identity binding nor has a live Apple round trip. Existing workspaces use the Product Owner-approved *limited trust* Internal Alpha enrollment. Never auto-rebind another SIWA identity to the workspace.
- The recovered report's P-256 **signing** key cannot encrypt payloads. D1 approves TLS + minimal server-readable temporary processing; storage access / at-rest encryption still must be explicitly controlled. Never claim end-to-end encryption.
- One invitation, not one request, is the DB contention point. Grant uniqueness on invitation is mandatory; transaction must lock invitation and evaluate expiry **after waiting for the lock** with a current DB clock expression, not cache an expiry result from outside the transaction.
- Supabase `verify_jwt=true` validates Supabase-auth JWTs, **not** arbitrary Apple identity tokens or custom Vǫxtr bearer tokens. For a Vǫxtr custom-authorized function, `verify_jwt=false` may be required to let the request reach a handler that independently validates an Apple token/session or signed proof. This flag is only platform admission and **must never be treated as application authorization**. The foundation `health` endpoint is public and must never be copied into a data endpoint. Prefer separate function entrypoints for anonymous requests and sensitive operations, plus fail-closed middleware verified by negative tests. Do not claim all auth endpoints can safely keep platform `verify_jwt=true` without confirming credential semantics. Current Supabase auth documentation must be checked against pinned CLI/runtime versions before implementation.

## C. Proposed identity and parent enrollment contract (implementation choice, not new product decision)

1. Backend verifies SIWA ID token using Apple's rotating JWKS and the **configured app identifier(s)** for audience; validate signature algorithm, issuer, audience, expiry, appropriate nonce and token issuance window. Reject substituted subject/email/name. Use Apple `sub` as credential identity only, never as CloudKit identity or the iOS `AccountId.pending` sentinel. Each onboarding attempt is bound to a fresh server nonce and expires; replayed nonce fails. SIWA identity alone does not prove existing-workspace ownership.
2. **New workspace**: only a coordinated, authenticated creation pathway binds the newly created stable workspace ID and SIWA subject in one reviewed lifecycle. Reject client-provided arbitrary `workspaceId` registration as proof of creation; add an explicit iOS-domain creation integration gate rather than a backend-generated duplicate workspace. No 'first registration wins' by UUID.
3. **Existing workspace Internal Alpha**: Parent-initiated enrollment displays workspace ID/name locally and requires deliberate human confirmation; backend verifies SIWA identity and refuses an already-bound workspace with a different subject. Because a guessed ID + matching display name can otherwise be claimed, restrict enrollment to explicitly authorized Internal Alpha participants / operator-controlled provisioning and record auditable enrollment provenance; the actual verification/provisioning method must be reviewed before accepting any real existing-workspace claim. This step is **limited trust, not cryptographic proof**; product approval of a limited trust step does not magically make arbitrary self-service binding secure.
4. Parent owner-account replacement/second guardian requires a separate reviewed administrator-mediated operation with evidence and audit, not automatic rebind or inferred membership. Enrollment and invitation issuance require server-checked workspace binding. Parent session must be workspace-scoped and server-invalidatable. Never use profile email/name as authority.

## D. Proposed device credential and authorization wire baseline

Stable `v1` path family from recovered report is a candidate, not yet accepted public API. Use JSON UTF-8 over HTTPS; `Cache-Control: no-store` on all auth, code and hydration responses; do not place invitation IDs in web analytics or URLs transmitted to third parties. QR contains a version and random invitation ID only, no athlete/participant IDs or PII. All externally supplied UUID/key/string/body sizes and content types have explicit limits; reject unknown required-field types; generic public errors do not enumerate athlete/workspace membership.

1. Athlete creates a unique P-256 Secure Enclave signing key for the installation. Request creation binds the normalized public key bytes to one invitation/request ID; server returns a cryptographically random comparison code in the **direct response**. Only a workspace-authenticated Parent list reveals that request's code; codes expire with request and are not credentials. Parent verifies the actual device's displayed code and approves only its exact request ID; all others remain unapproved/are explicitly rejected on consumption. A physical comparison remains human judgment, not proof of the athlete's real-world identity.
2. Proposed challenge: server creates a CSPRNG 32-byte nonce, records request/grant ID, action, scope, issued/expiry and one-use state, expiry **60 seconds** (engineering default). Client signs explicitly versioned unambiguous UTF-8 canonical fields including HTTP method, route, request/grant ID, action, nonce, deadline and SHA-256 hash of exact request body; server verifies ECDSA P-256 SHA-256 signature against the stored authorized key, canonical format, nonce freshness and one-use state. Signature encoding and public-key format must be specified byte-for-byte and proven interoperable Swift CryptoKit ↔ backend WebCrypto before this default becomes normative. Never sign or validate just a naked nonce with no purpose/scope.
3. Proposed server sessions: random 256-bit opaque tokens, **10-minute** TTL as engineering default, only keyed hash in DB; bound to one Parent/workspace or one active grant/requested device, permissions and expiry. Store client token `ThisDeviceOnly` Keychain, not UserDefaults. A bearer token can be stolen and used before expiry: for **hydration and grant refresh**, require a fresh device-key signature in addition to active session; validate active grant on every sensitive call. On relaunch attempt live verification before presenting current access as verified. Session TTL is not an offline viewing lifetime. Stronger proof on all sensitive calls can be chosen during implementation review; do not claim bearer token alone provides device binding.
4. Client application must not treat an HTTP 200 from an untrusted endpoint as proof of grant or cross-domain membership. Verify actual selected stable IDs before hydration upsert; refuse conflicts and duplicate athlete identity. Never fabricate a local session when backend is unreachable.

## E. Proposed state-machine and transaction contract

Invitation: `issued -> consumed` or expires by authoritative time; `revoked/cancelled` optional only if explicitly supported. Request: `pending -> approved | rejected`, `approved -> claimed` upon grant commit; expiry and invitation consumption invalidate all further initial claims. Grant: `active -> revoked` (no reactivation), reference to exactly one chosen request, invitation and canonical IDs. Session: `active -> expired | invalidated`; server checks underlying grant every time. Hydration escrow: `pending/available -> acknowledged_deleted | expired_deleted | revoked_deleted`; distinguish logical denial from physical/backup deletion. If the schema requires terminal-state rows, define retention separately from hydration PII retention.

**Atomic first claim:** authenticate signature and nonce, begin DB transaction; explicitly lock invitation row (`FOR UPDATE OF i` or direct `SELECT ... FROM invitations ... FOR UPDATE`); after lock, use a fresh DB-time reading (`clock_timestamp()` or equivalent) for `expires_at > now`, check invitation not consumed, chosen request still approved and matching key, no earlier grant; insert active grant with `UNIQUE(invitation_id)`, set invitation consumed and request claimed in the **same transaction**; commit once. On uniqueness/serialization conflict, fetch existing grant only after re-authenticating the identical public key/request and checking active/recovery window; never return one request's payload to another. Ensure nonce consumption is atomically one-use without making a lost-response retry impossible: retry obtains a new challenge and resolves the existing committed grant by **same verified key**, not by resubmitting an old signature.

Concurrent Parent approve/reject and Athlete claim must use consistent row-lock order or a single serialized invitation transition; a late approval does not resurrect an expired invitation. Test competing approved requests, two simultaneous claims, response loss, expired-at-lock-acquisition, revoke-versus-retry, replay and server crash boundaries against **real isolated PostgreSQL**; mock-only success is insufficient.

## F. Proposed 24-hour recovery and data-handling contract

Approval and optional Parent snapshot submission require the correct Parent session/workspace and exact selected IDs. No PII in invitation/request metadata, display-code list or public errors. A minimal hydration snapshot, if needed, is stored in private restricted escrow, tagged to the exact approved request/grant, encrypted at rest using server-managed controls; the backend may access plaintext per D1. Snapshot fields must be verified against actual nonoptional SwiftData initializers and minimised; the old report's inventory is not yet a validated new hydration schema. Secrets/tokens/payload not logged, echoed in error traces or stored in publicly exposed tables.

Initial grant creation still requires invite age < 15 minutes. On first committed grant set fixed `recovery_deadline = grant.created_at + 24 hours` by server time, never extended by retry. An approved request with no committed grant cannot be claimed after invitation expiry and its unclaimed escrow must also be purged on a separate bounded short expiry (never wait indefinitely for a grant that did not happen). Recovery after commit requires **same request + live grant + fresh proof of same key + valid session + before deadline**; never create a second grant. Authenticated, idempotent hydration-complete acknowledgement clears escrow; revocation denies access immediately and marks escrow for purge. Deadline expiry denies all reads synchronously even if background cleanup is delayed; ensure monitored eventual physical row purge, and disclose that backup snapshots may persist under provider retention beyond row deletion. **Do not claim physical deletion 'no later than 24 hours' if backup retention or failed cleanup makes that false**: the hard 24-hour guarantee is access denial, and row deletion must be engineered/monitored with an operational limit explicitly reviewed before real data use.

## G. Proposed endpoint responsibility / HTTP outcome matrix

These paths are **draft names** that can change during final API review. Every handler performs its own role/scope/state checks; use `POST` for mutations with idempotency binding where necessary.

| Route family | Actor | Core checks / successful outcome |
| --- | --- | --- |
| Parent enrollment and session | SIWA Parent | Apple token verified; explicit new vs existing ownership path; workspace-bound session; collision -> deny + controlled recovery. No client `recordChangeTag` proof. |
| Invitation create | Enrolled Parent | Canonical exact IDs, workspace scope, server 15-minute expiry -> opaque invitation ID only. |
| Invitation request | Anonymous QR holder | Rate/size limits; valid invitation; bind installation public key; code only to that request. |
| Pending requests | Enrolled Parent | Workspace scope; code visible here, never in anonymous listing. |
| Approve/reject | Enrolled Parent | Compare real device; exact request; serialize selection; PII escrow only in protected Parent upload. |
| Challenge/claim | Approved installation | Request-bound nonce and key signature; atomic invitation grant; same-key idempotent retry only. |
| Hydration fetch/ack | Active grant + proven key | Exact ID scope, authenticated access, expiry/revocation, 24-hour cutoff; ack deletes escrow. |
| Grant status/session refresh | Correct grant + proven key | No bare `grantId` authorization, fresh proof, grant status checked. |
| Revoke | Workspace Parent | Server transaction `active -> revoked`; invalidate active sessions; deny all subsequent online protected access, escrow purge. |

HTTP baseline: `401` missing/invalid identity, `403` authenticated but wrong workspace/grant, `404` generic unknown/expired anonymous invitation (same body/timing policy), `409` conflict/already claimed by other request, `410` known expired *only when caller is already authenticated/authorized*, `429` rate limit, `5xx` safe non-PII failure. Suppress raw SQL/Apple errors in clients and logs. Revoke or expiry must not return cached hydration via CDN/proxy; no-store plus server state check, and minimize request/correlation logging of IDs.

## H. Technical security and operational gates

- Private backend `authz` schema; no auth table exposed through PostgREST/Data API, `anon`/`authenticated` USAGE/table/function grants revoked, RLS/default deny where applicable. Define an explicit privileged DB role/entry point; no service-role secret in iOS. Schema privilege tests must run against actual migrated isolated DB. Review Supabase default exposed schemas and effective grants, not only dashboard toggles.
- Secure random identifiers, codes, tokens; challenge one-use and rate limits by invitation/request plus deployment-supported IP/device abuse controls, with privacy-safe logging and no lockout based on guessable family identifiers alone. Set concrete thresholds after operational threat review, not invented as approved product rules.
- CI gate: real migration reset/apply, privilege/exposure assertions, SQL race and failure injection, API negative auth and payload leakage, key encoding Swift↔backend interoperability test. Do not call mocked Apple/Secure Enclave verification an actual Apple integration test. No real family data in `voxtr-auth-dev`.
- Runtime gate: Codemagic builds and TestFlight on two physical iPhones: genuine SIWA flow, correct sibling binding, duplicate requests, interrupted rehydration within and after window, offline indicator, revocation, reinstall; independently exercise actual CloudKit transport/access after revoke. If business sync bypasses backend revocation, **stop release** and define a separate consent/access integration; backend session revocation alone must not be called end-to-end access revocation.

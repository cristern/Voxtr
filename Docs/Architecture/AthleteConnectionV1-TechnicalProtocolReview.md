# Athlete Connection V1 — technical protocol review for approval

**Status: ENGINEERING PROPOSAL, not an approved or implemented API.** 2026-09-21. Read with [approved behavior/security contract](AthleteConnectionV1-NormativeSecurityContract.md), [decision ledger](AthleteConnectionV1-DecisionReview.md) and [historical corrected API inventory](AthleteConnectionV1-RecoveredAPIContract.md). Product Constitution → living Architecture → ADR remain authoritative. This document does not authorize code, migrations, deployments or merge.

## 1. Purpose and evidence

Connect one Parent-selected existing athlete to one physically verified installation, with 15-minute backend-enforced invitation, Parent approval, one grant, same-device 24-hour recovery and server-side online revocation. The service owns only authorization; it does not become a second profile, participant, activity or reflection source. A backend grant cannot by itself revoke CloudKit permissions or erase offline bytes. A production-ready end-to-end claim depends on separately proving CloudKit business-sync access enforcement.

**Repository inspection at `cristern/Voxtr` develop**: `Sources/VoxtrAppShell/AthleteIdentityHydrationService.swift` hydrates ParentProfile, FamilyWorkspace, workspace-owner WorkspaceParticipant, athlete AthleteProfile, intended-athlete WorkspaceParticipant and local `AthleteAccessGrant`, using stable IDs and explicit conflict checks. `Sources/VoxtrCore/CloudKit/AthleteConnectionInvitationCloudRecordMapping.swift` currently carries eleven values: `workspaceId`, `intendedParticipantId`, `intendedAthleteId`, `parentId`, `parentGivenName`, `workspaceDisplayName`, `ownerParticipantId`, `athleteGivenName`, `athleteBirthDateISO`, `athleteTimeZoneId`, `athleteDevelopmentStage`. This is **legacy CKShare transport**, not a validated backend payload schema. Future hydration must verify each required field against actual initializer declarations at implementation HEAD. Existing local `AthleteAccessGrant` is a domain access relationship and **must not be mistaken for** the backend's installation grant; owner participant semantics and access grants need an explicit integration adapter. Existing hydration parsing errors can embed an invalid raw date in an error reason; sanitize in the new integration before exposing logs/errors. All five/six upsert steps must remain ID-stable and resumable, never fabricate an athlete, family or new device grant.

## 2. Five architecture findings

1. Client-returned CloudKit `recordChangeTag + nonce` is **not server-verifiable ownership evidence**. The merged CloudKit token spike did not prove SIWA↔CloudKit identity binding or a live Apple round trip. Existing-workspace Internal Alpha registration therefore remains a limited trust workflow, not cryptographically proven ownership.
2. P-256 **signing** keys are not encryption keys. D1 permits minimal postapproval data handled temporarily by trusted backend over TLS; at-rest access/retention must be described truthfully.
3. Contention is the invitation row. Enforce one grant/invitation through lock and uniqueness; determine expiry with database time freshly sampled after acquiring lock, not a stale value computed before waiting.
4. Supabase platform `verify_jwt=true` validates Supabase-compatible JWTs, not arbitrary SIWA ID tokens or our custom sessions. A custom-auth Edge Function may need `verify_jwt=false` to admit a request, then **independently validate** its intended credentials and authorization at application layer; that flag is not permission to skip authentication. Separate public request and privileged data routes with fail-closed middleware and negative tests. The public foundation `health` function cannot be copied into sensitive handlers.
5. The existing CloudKit business-sync sharing permissions and future revocation path are separate from our authorization DB. Until audited and tested, do not claim backend grant revocation blocks CloudKit access or synchronized data. This is a release gate, not a reason to add business-data replication to Supabase.

## 3. Identity, enrollment and sessions — recommended implementation defaults

**Parent SIWA:** backend checks token signature using Apple's rotating JWKS, issuer `https://appleid.apple.com`, configured audience and expiry, and a server-issued nonce tied to the authentication attempt, plus reasonable issuance time. `sub` is credential identity, not CloudKit ID and not a replacement for the `AccountId.pending` sentinel without explicit iOS migration. Email, display name, UUID knowledge and client-returned CloudKit tags are not independent ownership evidence. Backend issues a short-lived server session bound to enrolled workspace and revocable server-side.

**New workspace:** binding the SIWA subject must be coordinated with actual canonical workspace creation, not a first-claimer POST accepting an arbitrary workspace UUID. Preserve business ownership in the iOS domain; backend credential mapping cannot create a second owner of the business concept. Require an inspected iOS creation integration before this endpoint is implemented.

**Existing workspace Internal Alpha:** explicit Parent action shows local workspace/display name and requires confirmation, backend verifies SIWA, then checks that existing binding does not conflict; allow enrollment only for individually authorized alpha testers through a reviewed operator-provisioning mechanism. A guessed UUID + public/guessed name alone must not suffice to seize an unbound workspace, even in Alpha. This is limited trust, not a cryptographic owner proof. Account change, contested enrollment and second guardian require separate operator-controlled verified recovery; no automatic rebind. Exact provisioning/evidence procedure remains a review blocker before enrolling real existing workspaces.

**Athlete key and challenge:** each installation creates its own P-256 Secure Enclave signing key and submits only normalized public bytes. Comparison code is random per request, returned solely to the requesting device and displayed only on authenticated workspace Parent request list. Parent compares physical device and approves exactly one request. Proposed challenge: CSPRNG 32-byte nonce, **60-second** lifetime, one-use and scoped to request/grant, method, path, action, expiry and SHA-256 of exact request body in versioned canonical bytes. Signature ECDSA P-256 SHA-256 verified against approved public key. Before freezing, specify exact UTF-8 format, field delimiters, signature encoding and public-key format and prove Swift CryptoKit ↔ backend WebCrypto vectors; never sign an unscoped nonce alone. Signatures prove device-key possession, not athlete identity.

**Sessions:** proposed opaque random 256-bit token, **10-minute** expiration, hash-only DB storage, Parent/workspace or athlete/grant scope, client stores token in `ThisDeviceOnly` Keychain. Token theft can allow misuse until expiry: require fresh device-key challenge for hydration retrieval and grant refresh, and check currently active grant for **every** sensitive online operation. Do not imply grant ID or bearer token alone proves physical device identity. After reinstall/key loss, new pairing is required. On relaunch attempt online revalidation before displaying a verified state; offline cached content can still be viewed under approved D3 policy. Token TTL and 60-second nonce are *engineering proposals*, not approved product numbers.

## 4. Proposed state-machine and database design

`invitation`: issued -> consumed, or time-expired (expiry check against clock; optional explicit canceled requires separate API); fixed canonical workspace/participant/athlete scope.

`request`: pending -> approved or rejected; approved -> claimed only with successfully committed grant. Grant creation disables competing initial claims. Approval and claim/rejection operations require consistent locking order around invitation so concurrent actions cannot approve another device after consumption.

`grant`: active -> revoked, irreversible, exactly one approved request and public key, `UNIQUE(invitation_id)` mandatory. `session`: active -> expired/invalidated, never membership. `escrow`: available -> acknowledged/expired/revoked and ineligible for access immediately at deadline, with separately monitored physical deletion. Distinguish persistent local domain `AthleteAccessGrant` from backend installation grant.

**Atomic first claim:** verify fresh challenge and key; begin DB transaction; lock invitation row explicitly (`SELECT ... FOR UPDATE` on invitation alias `i`); **after lock** read database clock (`clock_timestamp()` or separately executed clock read, rather than a pre-lock `now()` timestamp) and check `expires_at > db_time`, approved exact request/public key and no consumption; insert grant, consume invitation and mark request claimed in *one* transaction. Unique `grants(invitation_id)` is independent backstop. Commit once. Repeated claim from same exact request/key gets fresh challenge; after proof, returns same active grant only within the recovery window, never creates another. Wrong request/key, revoked grant or elapsed recovery deadline receive no payload. Nonce must be one-use; lost-response retries use a new nonce. All state transition and idempotency outcomes require real isolated PostgreSQL tests, including competing requests, lock waits, failure injection, concurrent approve/reject and revocation race.

Private schema, role privileges, default deny/RLS and Data API exposure must be verified by an actual migration test; no direct `anon`/`authenticated` access, broad security-definer grants or service-role key in iOS. Backend grant/session tables do not become canonical AthleteProfile/WorkspaceParticipant tables. Suggested constraints: foreign keys for request→invitation, grant→approved request/invitation, unique invitation grant, checked statuses and valid timestamps, immutable identity scope, monotonic revocation. Exact DDL must be reviewed before migration.

## 5. Recovery, hydration and retention

Invitation must be valid for **first** successful grant (<15 minutes). At that commit set immutable `recovery_deadline = grant.created_at + 24 hours` using DB time; it never refreshes on retry. Approved snapshot submission is workspace-authenticated and exact-request-scoped; if an escrow exists **before** grant issuance it must have its own invitation-bound short expiry and cleanup to avoid orphaned minor PII. Pending requests, QR and public responses contain no descriptive profile data. Hydration snapshot minimum field inventory is the eleven legacy fields listed in §1 **subject to initializer-based pruning/confirmation**, never an automatically approved copy of the old CloudKit record.

Protected HTTPS delivers only to live authorized grant and **fresh key proof** of the same approved installation. Backend can access plaintext per D1; any persisted payload must be encrypted at rest and restricted from Data API/anonymous access, logs, backups and broad service roles. Same-key retry may redeliver until fixed deadline while grant active; verified idempotent `hydration-complete` ack deletes active escrow early, revocation denies immediately and triggers purge; synchronous server read denial after 24h is mandatory regardless of cleanup lag. Row deletion does **not** destroy immutable provider backups immediately: before use of real family data, document actual encryption, retention, backup purge semantics, and monitoring of failed cleanup. If 24-hour physical deletion from *all copies* cannot be guaranteed, do not claim it or silently weaken the approved user-facing deletion outcome; return this as an explicit implementation/provider acceptance issue. An expired unclaimed invitation needs separate short retention/no orphan escrow; same-device retry cannot resurrect a grant that was never committed.

Hydration must preserve stable IDs, reject conflicting preexisting SwiftData graph, not create a new athlete identity, and not fabricate a local active participant or backend grant. Full-state status on device must reflect live backend authorization, not local state. CloudKit business sync remains separate and requires independent enforcement before release.

## 6. Draft endpoint responsibility matrix (names not frozen)

| Endpoint family | Caller | Essential security condition |
| --- | --- | --- |
| Parent enrollment/session | SIWA Parent | Verify Apple JWT/nonce; authorized new vs existing workspace path, no first-register-by-UUID. |
| Invitation create | Workspace-enrolled Parent | Exact canonical IDs; DB-time TTL; QR gets opaque ID only. |
| Invitation request | Anonymous QR holder | Valid invite; bounded key/body/rate; own code only in direct HTTPS response. |
| Pending request list | Workspace-enrolled Parent | Codes of that workspace only, no anonymous enumeration. |
| Approve/reject | Workspace-enrolled Parent | Explicit selection, serialized invitation transition, protected upload of minimum snapshot. |
| Challenge + claim | Approved Athlete installation | Fresh signed bound nonce; DB atomic consume/grant; same-key retry only. |
| Hydration get/ack | Active correct grant + key proof | Exact selected IDs, 24h cutoff, revocation check, ack clears escrow. |
| Grant status/refresh | Matching grant/key | Scope, active server grant, fresh signature for refresh. |
| Revoke | Workspace-enrolled Parent | Server atomically revokes, invalidates sessions, denies future protected backend access. |

Use versioned JSON over TLS; sensitive responses `Cache-Control: no-store`. UUIDs, codes, tokens never sent to third-party telemetry; input lengths/content types bounded. Generic public unknown/expired response with no enumeration; 401 missing auth, 403 scope mismatch, 409 conflict, 410 expired only to authorized callers, 429 abuse and sanitized 5xx failures are engineering baseline. Exact URL/HTTP fields and serialization require final integration review; legacy report paths are candidate names, not approved schema.

## 7. CI, operational and release gates

- Isolated backend CI: actual DB migration/apply/reset, SQL lock/uniqueness races (including expiration under lock), permissions/exposure, no anonymous minor PII, wrong workspace/Parent and stolen QR/request/grant, challenge replay, revoked active-session denial, same-key retry and 24-hour cutoff, failure-injected storage and scheduled cleanup. Distinguish mocked Apple from a live SIWA test and simulated signatures from actual iOS Secure Enclave key generation.
- Auth handler validates each credential itself when Supabase platform JWT gate is disabled for custom auth; `health.verify_jwt=false` is not a reusable auth configuration. Pin supported runtime/SDK versions and confirm relevant Supabase guidance for custom sessions before implementing.
- Codemagic is Swift compile authority; two real iPhones with TestFlight must prove selected athlete/sibling isolation, code comparison, interruptions, relaunch, offline message, revoked backend calls, reinstall and **separate CloudKit sync access after revoke**. If CloudKit remains a bypass, stop release and decide integration; do not solve by duplicating all business data into backend.
- No real child/family data in Supabase development project. No hosted config change, SQL migration, app behavior or deployment in docs PR #97.

## 8. Disposition and next bounded task

**This is a concrete technical proposal, not a completed protocol approval.** Recommended engineering defaults are 60-second nonce, 10-minute session, versioned request-bound ECDSA challenge, explicit private DB authorization roles and metadata-only first migration. Before final approval, inspect iOS workspace creation and CloudKit sync code to resolve actual ownership/integration; prove Swift↔Deno signature wire vectors; document escrow backup deletion capabilities and alpha enrollment provisioning. These are security review gates, not a reopening of approved D1–D4 product outcomes.

If reviewed, first Claude task is metadata-only DB migration plus real isolated SQL concurrency/privilege tests, in fresh `claude/...` branch from backend `develop`; no hydration PII storage or hosted deployment until escrow/security review, and never auto-merge. Do not treat PR #97 merge as approval of backend implementation.

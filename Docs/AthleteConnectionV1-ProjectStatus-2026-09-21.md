## New repository-confirmed integration facts and actions

Inspection of actual `develop` files `Sources/VoxtrAppShell/AthleteIdentityHydrationService.swift` and `Sources/VoxtrCore/CloudKit/AthleteConnectionInvitationCloudRecordMapping.swift` confirms current bootstrap hydrates `ParentProfile`, `FamilyWorkspace`, owner `WorkspaceParticipant`, selected `AthleteProfile`, selected athlete `WorkspaceParticipant` and a local `AthleteAccessGrant`; projection has `workspaceId`, `intendedParticipantId`, `intendedAthleteId`, `parentId`, `parentGivenName`, `workspaceDisplayName`, `ownerParticipantId`, `athleteGivenName`, `athleteBirthDateISO`, `athleteTimeZoneId`, `athleteDevelopmentStage`. This is **legacy CKShare payload**, not an approved backend schema. Reconcile required fields against model initializer signatures at implementation HEAD; never copy entire record shape blindly into anonymous request or logging. Local domain `AthleteAccessGrant` is not automatically the new backend installation/device grant; preserve separate authorities and transition ownership. Existing hydration error includes raw unparseable date in an error reason: scrub from future logs/public responses; do not claim already fixed.

The old Foundation B closeout documents an earlier CKShare-first direction that is superseded **for pairing authorization only**, not proof that all business CloudKit sync can be revoked through the new backend. The real CloudKit sync authorization / revoke integration is a release blocker if it grants access outside backend checks; audit before claiming end-to-end secure pairing/revocation. Legacy `technicalOwnerAccountId = AccountId.pending` must not be interpreted as verified SIWA owner, auto-migrated or silently rebound.
